# 配方与 Netlify 发布收口设计

日期：2026-08-18

## 目标

在不扩张现有三类器具（铁锅、蒸屉、砂锅）的前提下，修正小游戏配方判定、用户点名的数据问题和发布性能问题，使生产构建能够发现重复配方、失效详情链接与误发布的大图。

## 范围

### 配方判定

- 使用“器具相同且实际食材名称集合与配方食材名称集合完全相等”作为匹配条件。
- 同一组合如果匹配多道菜，界面同时展示全部匹配结果，不依赖 JSON 中的排列顺序。
- 食材重复投入不改变集合匹配结果，但仍受每个器具最多五次投入的限制。
- 没有完全匹配时保持现有失败提示与清空器具行为。

### 数据调整

- 从小游戏配方和山东菜品详情中删除“二月二杂粮粥”；相关原始图片不删除，但不再作为页面内容引用。
- 煎饺抱蛋：蒸屉改为铁锅。
- 耳朵眼炸糕：砂锅改为铁锅。
- 熟梨糕：砂锅改为蒸屉。
- 红烧牛窝骨：铁锅改为砂锅。
- 茶汤没有可准确表达“铜壶冲制”的现有器具，保留砂锅作为游戏化近似。
- 煎饼果子：猪肉改为葱，并同步天津详情数据。
- 王哥庄大馒头：删除糯米，保留面粉和鸡蛋，并同步山东详情数据。
- 八珍豆腐：加入豆腐；食材柜启用现有豆腐素材，并同步天津详情数据。
- 不继续改写其他菜品的食材内容。

### 多结果展示

- 单道匹配继续使用现有菜品详情弹窗。
- 多道匹配使用同一遮罩层展示每道匹配菜的缩略图、名称、食材和详情入口。
- 弹窗支持关闭按钮、点击遮罩关闭和 Escape 关闭；详情入口保持现有页面路由。

### 图片与发布性能

- 从现有食材 PNG 机械缩放生成最长边 240 像素的 WebP，保留透明通道。
- 游戏食材柜、拖拽克隆和器具托盘统一引用 WebP，包括豆腐。
- 源 PNG 保留在源码目录，便于以后重新导出。
- 构建完成后，从 `dist` 排除 `assets/images/ingredients/*.png` 与 `assets/images/kitchen/*.png`；页面仍需要的宣纸纹理 PNG 不受影响。

### 构建与部署

- 发布校验交叉检查配方详情链接、缩略图、食材名称和完全相同的器具＋食材签名。
- 发布校验确认食材和厨房原始 PNG 未进入 `dist`。
- `_headers` 为 `/` 增加与 HTML 相同的 `Cache-Control` 规则。
- 部署指南把实践页示例改为 `practice.html?province=anhui`。
- 不自动提交或推送 GitHub；验证完成后由用户决定提交和推送时机。

## 验证标准

1. 每个保留配方用其精确食材集合均能返回自身；没有配方被前序项目抢占。
2. 人工构造两个相同签名配方时，匹配函数返回两个结果。
3. “二月二杂粮粥”不再出现在配方表、山东列表或发布数据中。
4. 豆腐出现在食材柜中，八珍豆腐必须包含豆腐。
5. 所有配方详情链接和缩略图均存在。
6. 桌面与手机尺寸下游戏可加载，首页跳转与后退回归不受影响。
7. `npm run build` 通过，`dist` 不含上述原始 PNG，发布体积显著下降。

## 非目标

- 不新增第四种器具或铜壶交互。
- 不全面重写其余菜品的历史配方。
- 不删除源码中的原始 PNG。
- 不在本次改动中自动部署 Netlify 或推送 GitHub。
